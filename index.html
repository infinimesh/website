The device layer for your IoT and AI stack.

infinimesh handles device identity, access and state. Your data goes to the tools you already use: Kafka, Postgres, InfluxDB, a webhook. No dashboard you have to adopt. The open source core is complete and free. No feature is held back for a paid tier.

How it works

Devices connect over MQTT 3.1.1 or 5, or send their own JSON over HTTP with POST /v1/ingest and a device token. The bridge checks the device certificate and topic. The shadow keeps reported and desired state. Addons read the stream and write it where you want it.

Access is the data model

Accounts, namespaces and devices form a graph. Share a namespace with a customer at READ, and with their service partner at MANAGE. Each one sees their devices and nothing past them. This is in the open source core, not a paid tier.

Relevant if you sell connected products in the EU and need to give customers access to their device data under the Data Act. infinimesh gives you the access model. It does not make you compliant by itself.

Who it is for

Device makers

You run your own backend and need each customer, and their partners, to see only their devices.

Teams with a data stack

You already have Kafka, Postgres or a warehouse and want devices to feed it, not a second dashboard.

Self-hosters

You want the backend on your servers, under Apache-2.0, without a price list per device.

Stable v1 API

REST under /v1, gRPC and Connect from one proto schema. Breaking changes are checked against the v1.0.0 tag. Versioning policy, API reference.

When not to use it

You want an all-in-one UI

No dashboards. Rules and alarms on device state are in core, but charts are up to you. Use Grafana on top of an addon, or ThingsBoard.

You need OTA inside the core process

Firmware delivery is a separate addon you build: hawkBit, Mender, or a signed webhook. None of them is a published image.

You need an HA broker cluster now

Bridge sessions can live in Redis, so a restart keeps them. A tested multi-replica broker cluster is not there yet.

New in 3.4

Rules and alarms

A CEL condition on device state, such as reported.temp > 70, raises an alarm. Ack and clear it in the console, the API or inf alarms. Cooldown and repeat stop alarm storms. Rules docs.

OTA contract

Core stores the target version per device and the status the device reports back. An OTA addon registers through the plugins API first, then the namespace switch turns on. hawkBit, Mender, and the signed webhook addon do the delivery. You build them. OTA docs.

Audit and quotas

Alarm, plugin and OTA actions are logged with who did them. Each namespace can cap devices and messages per second. Zero means no limit.

CoAP and Redis sessions

A CoAP gateway takes JSON on UDP 5683 for small devices on a private network. MQTT_SESSION_STORE=redis keeps bridge sessions across restarts. CoAP docs.

3.4.1: OTA requests and a reliable stream

An account asks for a firmware version and the OTA addon sets the target. On reported state the addon token can write only reported.ota, and inf plugins rotate replaces it. The shadow stream keeps every update across reconnects, with a 256-event replay window per namespace and a full resync after a larger gap. Changelog.

3.4.2: OTA addons released

The hawkBit, Mender and signed webhook addons are released in addons v3.4.2. You build them from source. There are no published images. Core 3.4.2 lets the webhook addon token read its namespace webhook URL, so the webhook addon needs core 3.4.2 or newer.

Addons

Each addon is a small separate service that reads device state and writes it out. Writing your own is mostly reading one stream: one stream per account or namespace, with device added and removed events, and an event id on every message so retries can drop duplicates. A read-only streaming token lets a long-running addon follow it without a per-device token. Stream docs, addons repo.

hawkBit OTA

Assigns a distribution set for a requested version. Released in addons v3.4.2. You build it. It is not a published image.

Mender OTA

Creates one deployment of the requested artifact on the open source Management API. Released in addons v3.4.2.

Signed OTA webhook

Posts OTA and membership events, and accepts a target or a report. Released in addons v3.4.2. Needs core 3.4.2 or newer.

AI ready

AI agents and LLMs need device data with the same access rules as people. infinimesh has that model already. Device state will be available to AI agents over MCP and to any LLM through addons, scoped by the same permission graph. An agent sees only the devices its token can see.

You can run models locally with vLLM or Ollama, so device data stays on your servers. Hosted APIs work too, if you choose them.

MCP server coming soon

Read device state and set desired state from an AI agent, within the token's permissions. Not built yet.

LLM addon coming soon

Send device state to any OpenAI-compatible API: vLLM, Ollama, Mistral, OpenAI, Anthropic, Gemini. Not built yet.

Neither exists today. Until they ship, use the webhook or MQTT bridge addon to feed your own agent.

Quickstart

One machine with Docker Compose.

git clone https://github.com/infinimesh/core.git
cd core
cp .env.example .env
docker compose up -d

Open http://console.127.0.0.1.nip.io

Log in as infinimesh / infinimesh. Change the password right away.

CLI:

brew tap infinimesh/inf-cli https://github.com/infinimesh/inf-cli
brew install inf
inf login api.127.0.0.1.nip.io:443 infinimesh infinimesh --insecure-skip-verify

The local certificate is self-signed, so the CLI skips the check. Use a 3.4 CLI with a 3.4 core. The CLI guide covers quotas, rules, OTA and audit.

Then connect a device: ESP32 over MQTT, ESP32 over HTTP, Pico W, or curl. Small boards that time out on TLS: read the small-device TLS guide.
